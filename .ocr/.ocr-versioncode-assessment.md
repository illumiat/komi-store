# 评估：能否把版本判定简化成 versionCode 比较

**结论先行**：一处可以（已改），两处**不能**（架构约束，非代码偏好），另发现一处**该判却没判**的缺口。

---

## 一、根因：`versionCode` 在检测阶段根本不存在

`GithubRelease` 的字段（`core/domain/.../model/account/github/GithubRelease.kt`）：

```
id, tagName, name, author, publishedAt, description,
assets, tarballUrl, zipballUrl, htmlUrl, isPrerelease
```

**没有 versionCode。** GitHub API 只给 tag 与资源列表。

要拿到一个 release 的 versionCode，必须**下载 APK 并解析清单**。所以：

> **"检测阶段"（拿到 APK 之前）天然只能用 tag；
> "已拿到 APK 的阶段"才能用 code。**

这不是代码写得不好，是数据可得性的硬约束。

### 佐证：`latestVersionCode` 的全部来源都是"已观察到的 APK"

| 来源 | 文件 | 说明 |
|---|---|---|
| 一次性迁移归一化 | `InstalledAppUpdates.kt:87` | `withMigratedVersionInfo` |
| 自动更新下载后 | `AutoUpdateWorker.kt:212` | `withLatestSnapshot(versionCode = apkInfo?.versionCode ?: 0L)` |
| 外部导入本地 APK | `AppsViewModel.kt:1275` | `latestVersionCode = apkInfo?.versionCode ?: 0L` |
| 安装完成写库 | `InstalledAppsRepositoryImpl` | `latestVersionCode = resolvedLatestVersionCode` |

**没有一处来自远端候选 release。** 全部是"本地已实际存在过的 APK"。

## 二、逐处评估

| # | 位置 | 已装 code | 候选 code | 能否用 code | 状态 |
|---|---|---|---|---|---|
| 1 | `updateAppVersion`（#964，安装完成后） | ✓ DB | ✓ 参数（APK 已解析） | **能** | **已改** ✅ |
| 2 | `isDowngradeVersion`（#964，弹窗出现时） | ✓ DB | ✗ 需下载解析 | **不能** | 保持 |
| 3 | `UpdateVerdict.decide`（#934，检测时） | ✓ DB | ✗ API 只给 tag | **不能** | 保持 |
| 4 | `AutoUpdateWorker`（自动更新） | ✓ DB | ✓ `apkInfo.versionCode` | **能，但没判** | **缺口** ⚠️ |

### 关于 2：`isDowngradeVersion` 的现有设计其实是对的

它现在的兜底是：

```kotlin
// No ordering evidence, so don't claim a downgrade: the platform rejects a real
// one at install, while a wrong guess demanded an uninstall.
return false
```

**"无证据就不判降级"与你的思路同源** —— 都是拒绝猜测，把最终裁决交给平台（平台手里有真 code）。
所以它**不需要简化**：它已经是"tag 不可靠 + code 不可得"前提下的正确形态。

### 关于 3：`UpdateVerdict` 的入参印证了同一约束

```kotlin
data class Installed(tag: String?, versionCode: Long)        // 有 code
data class Stored(latestTag: String?, latestVersionCode: Long?)  // 有 code
data class Matched(tag: String, publishedAt: String?, isPrerelease: Boolean)  // ✗ 无 code
```

只有 `Matched`（候选 release）没有 code，其余都有 —— 与上表一致。

## 三、附带发现（不是简化，是缺口）⚠️

`AutoUpdateWorker` 手里**同时握着两个 code**：

- `apkInfo?.versionCode` —— 刚下载并解析出的新版
- 已装应用的 code —— 在 `currentApp` 里

**但它完全不做降级检查**，直接 `installer.install(filePath, ext)`（`AutoUpdateWorker.kt:221`）。

自动更新只在 `isUpdateAvailable = true` 时触发，而那个标志来自 **tag 比较**（本 PR 正在质疑其可靠性）。所以理论上存在"自动更新把旧版装上去"的可能。

**这是唯一"能靠 code 判、却没判"的地方。** 是否补这一处，取决于是否认为自动更新也需要降级防护 —— 属**功能决策**，不是简化。

---

## 四、建议

1. **不再扩大 code 化的范围** —— 2、3 两处做不到，也不必做
2. **第 4 处（`AutoUpdateWorker`）单独判断**是否需要降级防护（我倾向**先不动**：自动更新的语义是"装上检测到的新版"，而不是让用户选择；在那里拦降级会引入新的失败路径，且当前没有用户报告）
3. **`isDowngradeVersion` 保持现状**，但可以在注释里点明"code 在此时不可得"，避免后来者重复我这次的困惑

## 五、已验证的改动（本轮 #964）

`updateAppVersion` 中三处判据统一为 **versionCode 优先、tag 兜底**：

| 场景 | 已装 code | 要装 code | 结果 |
|---|---|---|---|
| 正常更新 | 100 | 200 | 非降级 ✓ |
| 主动降级 | 200 | 100 | **降级** ✓ |
| 装中间版 | 100 | 150 | 非降级（仍有更新）✓ |
| nightly 复用（更新） | 103733 | 103740 | 非降级 ✓ |
| **降级到旧稳定版** | 103740 | 200 | **降级** ✓（tag 无法判序，code 直接命中）|

决策表通过，构建成功。

### 后续修正（ocr 审出后）

上面最初的重构基于一个**错误断言**——我以为"只有完成的安装才会到达 `updateAppVersion`"。
ocr 审出这是错的：`saveInstalledAppToDatabase` 对**未完成**的安装（文件只是停放、等用户操作）
也会调用它，并传 `isPendingInstall = true`。若在那种情况下记录跳过，
就会为一个用户从未真正运行的版本隐藏更新。

修正：加 `!isPendingInstall` 作为门禁。这样既保住"全路径可达"（所有安装路径都汇聚于
`updateAppVersion`），又做到"仅安装完成后才记录"。

最终决策表 10/10 通过（含 pending 未完成 → 不记录、MajdataPlay 形态 → 记录跳过）。

## 六、决策记录（2026-09-21，用户裁定）

### 第 4 处 `AutoUpdateWorker` —— **驳回，不修**

理由（用户原话）：

> 这个驳回因为仓库行为不可预期，取决于用户怎么判断我们只求表面的，不要在奇怪的地方拦截

即：**本 PR 只处理表层**——用户在详情页主动选择旧版时的提示与放行。
自动更新属于另一条路径，仓库行为本身就不可预期（取决于上游怎么发版），
在那里加降级拦截属于**在边缘路径上自作主张**，超出本 PR 范围。

→ **结论：不在 `AutoUpdateWorker` 加任何降级检查。**

### 第 2 处 `isDowngradeVersion` —— **行为正确，设计如此**

用户原话：

> 这个 PR 的解决目的是防止仓库行为不在预期自动更新的范围内，又要求用户强制卸载所以行为无错

即：该函数无排序证据就不判降级的兜底**正是本 PR 想要的行为**——
防止上游仓库的非常规发版方式（复用 tag、无法排序的 tag）导致
应用**要求用户强制卸载**。它没有 bug，也不需要简化。

→ **结论：保持现状，不改。**
