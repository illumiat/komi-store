This PR fixes GitHub nightly update detection for releases that reuse opaque tags, especially a fixed `nightly` tag whose Release is deleted and recreated by CI.

### Detection changes

- Compare GitHub Release `publishedAt` timestamps when the matched tag is an opaque marker (`nightly`, `rolling`, …) or otherwise non-reconcilable — including CI re-publishing the same fixed tag. Ordinary semver tags keep pure version comparison.
- Evaluate the timestamp path before the normal version/code equality short-circuit.
- Preserve pre-release filtering so `nightly` is considered when `includePreReleases` is enabled.
- Treat tags carrying an unparseable hexadecimal tail (e.g. InstallerX `26.08.11f15e4`) as non-reconcilable, so they use the timestamp path instead of a bogus numeric comparison. This is the case in practice for InstallerX: its hash-tail releases are flagged as prereleases, which (together with the opaque/same-tag conditions) admits them to the timestamp branch. A non-reconcilable tag that is neither opaque, same-tag, nor prerelease stays silent rather than triggering a numeric comparison — deliberately, since nothing about such a release proves it newer.
- A release the user deliberately skipped is never re-offered, including an opaque nightly tag that CI re-publishes; the skip is cleared only by a strictly newer release.

### Refactoring

- Extract the update decision logic into `UpdateVerdict.decide()`, a pure domain module. It previously lived inline in `InstalledAppsRepositoryImpl.checkForUpdates()` — ~70 lines of pure judgement inside a method holding 8 dependencies and direct DAO/HTTP/file IO — which made every verdict regression verifiable only on a real device.
- `installedVersion` (the GitHub release tag) is now written only by install-owning events: real installs, system-confirmed pending resolutions, and the tag normalization that runs when the system reports a matching `versionCode`. External install sync and the update-check flow no longer overwrite it; the latter only fires when the installed `versionCode` already equals the matched release's (the package really is that build). This removes the tag/`versionName` semantic collision that repeatedly corrupted the installed-version baseline.
- Partition the `InstalledApp` write surface into zone-scoped update functions (`confirmInstall`, `resolvePendingFromSystem`, `normalizeInstalledTag`, `withMigratedVersionInfo`, `observeExternalInstall`, `markPending`/`clearPending`, `withLatestSnapshot`). A bare `copy()` with dozens of arguments previously let any writer overwrite fields owned by another writer; each zone function now copies only the fields of its declared zone. The migration zone (`withMigratedVersionInfo`) is deliberately cross-side — a one-time import normalizer that owns both sides' version name/code fields, never tags, flags, or assets. All full-row `copy()` writers were migrated; read sites and the Room schema (v18) are untouched. Ownership is pinned by 15 new unit tests.

### Detail page consistency

- Detail page initialization no longer hard-codes the STABLE category: the default selection derives from the installed channel (an app installed from a prerelease opens on the prerelease release), and the category is preserved across refreshes via a `firstInCategory` fallback.
- The install button label is now gated on opaque-tag-aware state, so an app with `installedVersion = nightly` no longer shows "update" on the stable release — tapping it would have installed the older stable build (a downgrade).

### Behavior on transient check failures

- Empty release window / no matching asset: update metadata is cleared for regular repositories (they self-heal, as before). For opaque-marker (nightly) repositories the flag is kept through transient failures — clearing it would drop the stored `publishedAt` baseline and make the next scan re-report the same release as a fresh update.
- A failed check still records `lastCheckedAt`, so retry pacing and the "last checked" UI keep working.
